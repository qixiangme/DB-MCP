# 비공개 데이터셋 채점 결과

`eval/private-eval.json`(신규 작성, `eval/official-eval.json`과 문항 완전 비중복) 30문항으로
Spring AI(baseline) / Go / Ktor 세 구현을 순차 기동해 채점했다. 채점 대상 코드나 프롬프트에는
이 문항을 노출하지 않았다.

## 프로토콜

| 항목 | 값 |
|---|---|
| 데이터셋 | `eval/private-eval.json`, SQL 10 / VECTOR 10 / GRAPH 10, ground truth는 `companyx-dataset-v1.0` SQL/그래프/문서에서 직접 조회해 도출 |
| 실행 순서 | baseline → Go → Ktor (동일 포트라 순차 기동, 각 구현마다 mcp-server 8081 + agent-app 8080 재기동) |
| 모델 | `gemma3:1b` (기존 벤치마크와 동일) |
| 채점기 | `eval/answer_rules.py` (기존 로직 재사용), `eval/bench-results/equivalence_check.py --eval-file` 옵션 추가 |
| 원시 결과 | `baseline-private.json`, `go-private.json`, `ktor-private.json` |

## 라우팅 미스 3건은 세 구현 공통

`PN6`(대구 지역 고객사 목록 → VECTOR로 오분류), `PV4`(Product-C4 백업 시각 → SQL로 오분류),
`PG2`(데이터플랫폼팀 부서장 → VECTOR로 오분류)는 baseline/Go/Ktor 세 구현 모두 동일하게
틀렸다. 세 구현이 라우팅 로직(`RuleBasedRouter`)을 1:1로 포팅한 결과이므로, 이는 구현 차이가
아니라 규칙 기반 라우터의 키워드 설계 자체가 못 잡는 질문 패턴임을 보여준다(포팅 정확성의
방증이기도 하다 — 셋 다 같은 자리에서 같은 실수를 한다).

## 결론 (gemma3:1b)

- baseline과 Ktor는 이 신규 비공개셋에서도 기존 공개셋 벤치마크와 같은 패턴(오답 문항 완전
  일치)을 재현했다 — 언어를 유지하고 프레임워크만 바꾼 포팅은 답변 동작이 사실상 동일함을
  다시 확인.
- Go는 공개셋에서는 baseline보다 낮았지만(43.3% vs 50.0%), 이번 비공개셋에서는 오히려
  1위(43.3% vs 40.0%)였다. 표본이 30문항으로 작아 통계적으로 유의미한 차이라 보기는 어렵고,
  "Go가 근소하게 우세하거나 baseline과 동등한 수준"이라는 게 두 데이터셋을 합친 더 정확한
  요약이다. 순위를 매겨야 한다면 이번 비공개셋 기준으로는 Go가 1위, baseline·Ktor 공동 2위다.

## gemma3:4b 재측정과 버그 수정 (baseline)

`gemma3:1b`는 세 구현을 저비용으로 비교하기엔 적합했지만, 답변 정확도 자체가 낮아
(40.0~43.3%) 시스템의 실제 답변 생성 품질을 보기엔 모델 용량이 병목이었다. baseline을
`gemma3:4b`로 재측정하고, 오답 12문항의 실제 응답 원문을 직접 까본 결과 구현 언어나
모델 크기가 아니라 **baseline 코드 자체의 버그 5건**을 확인해 수정했다.

| 단계 | 답변 정확도 | 라우팅 적중률 | 원시 결과 |
|---|---:|---:|---|
| gemma3:1b, 수정 전 | 40.0% (12/30) | 90.0% | `baseline-private.json` |
| gemma3:4b, 수정 전 | 60.0% (18/30) | 90.0% | `baseline-4b.json` |
| gemma3:4b, 버그 수정 후 | **90.0% (27/30)** | 96.7% | `baseline-fixed-90pct.json` |

### 발견하고 고친 버그

1. **`AnswerabilityGate`의 클레임 검증 오판** — "어디"(location_info), "누구"(person_identity),
   "가장 낮은/높은"(comparison_item_a/b) 클레임이 GRAPH 결과(Client-X 코드)나 SQL 최상값
   단일 행을 "커버 못 함"으로 오판해, 정답 근거를 이미 갖고 있었는데도
   "충분한 정보를 찾지 못했습니다"로 답변했다. GRAPH/SQL 소스 근거가 있으면 해당 클레임도
   충족된 것으로 판단하도록 완화했다.
2. **`DeterministicSqlPlanner`가 v2(production 경로)에 미연결** — v1(`AgentService`)에만
   연결되어 있고 `AgentServiceV2`는 항상 LLM 자유생성 SQL만 썼다. v2의 `generateSql`
   진입점에서 결정적 플래너를 먼저 시도하도록 연결하고, 없던 패턴("평균 연봉이 가장 낮은
   부서", "해지된 계약이 가장 많은 제품") 2개를 추가했다.
3. **`RuleBasedRouter` 키워드 누락** — "부서장", "모두 알려줘" 같은 표현이 라우팅 키워드에
   없어 SQL/GRAPH로 가야 할 질문이 VECTOR로 새고 있었다.
4. **`kg_search`의 predicate 체이닝 부재** — "클라우드사업부 부서장이 담당하는 고객사"처럼
   중간 엔티티(부서장 이름)를 한 번 거쳐야 하는 질문에서, 부서 전체 구성원의 결과가 섞여
   나오거나("부서장"이 predicate 키워드에 없어 필터링 자체가 안 됨) 빈 결과를 반환했다.
   질문에 predicate 키워드가 2개 이상 매칭되면 첫 번째로 중간 엔티티를 좁히고 그 다음
   predicate로 최종 결과를 찾는 체이닝을 추가했다. "이끄는"이 "이끌다" 활용형 매핑에서
   빠져 있던 것도 함께 고쳤다.
5. **답변 생성 프롬프트에 출처 필터링 지침 부재** — SQL과 GRAPH가 동시에 호출되면
   질문과 무관한 SQL 결과가 최종 답변에 섞여 들어가는 경우가 있어, "질문의 엔티티와
   실제로 일치하는 출처만 사용한다"는 지침을 시스템 프롬프트에 추가했다.

기존 오라클 테스트(`DeterministicSqlPlannerTest`, `AnswerabilityGateTest`,
`RuleBasedRouterTest`, `RetrievalToolsContractTest`)는 전부 통과해 회귀가 없음을 확인했다.

### 남은 오답 3건은 전부 VECTOR

`PV4`(문서 vs SQL 라우팅 경합), `PV9`(벡터 검색이 무관한 문서를 최상위로 골라
hallucination), `PV10`(벡터 검색이 관련 문서를 못 찾음)은 임베딩 유사도·청킹 단위의
더 깊은 문제라 이번 라운드에서는 수정하지 않았다.

## 일반화 검증: 30문항 수정이 실제로는 튜닝이었다

위 90.0%는 이 30문항에 대한 결과였고, 다른 문항에도 일반화되는지는 별도로 검증하지
않은 상태였다. 이를 확인하기 위해 `eval/bench-results/generalization_gen.py`로
`companyx-dataset-v1.0`의 부서(6)·제품(12)·지역(8)·업종(10)·카테고리(4)·규모(3) 등을
**전수 순회**하며 official/private 두 세트와 문항이 겹치지 않는 93개 질문을
생성했다(정답은 손으로 만들지 않고 DB에 직접 쿼리해 스크립트가 자동 도출). 각도는
같은 스키마를 다루지만 표현은 다르게 했다("사용하는" 대신 "쓰고 있는", "이슈보고"
대신 "문제를 제기한" 등).

**1차 결과(93문항, 위 5개 버그 수정만 반영): 라우팅 67.7%(63/93), 답변 정확도
68.8%(64/93)**로 폭락했다. 즉 30문항에서 만든 수정은 그 30문항의 정확한 표현에만
반응했을 뿐, 표현이 조금만 달라져도 실패했다 — **일반화되지 않은 튜닝**이었다.

### 실제 근본 원인: `RuleBasedRouter`가 아니라 `ROUTER_FALLBACK` 미사용

라우팅 실패 30건 중 24건은 "쓰고 있는", "문제를 제기한", "어떤 사람들이 있어" 같은
표현이 `RuleBasedRouter`의 고정 키워드 목록에 없어서 VECTOR로 새는 패턴이었다.
이건 키워드를 아무리 추가해도 표현의 조합이 무한해서 반복될 수밖에 없는 구조적
한계다. 저장소에는 이미 이 문제를 위한 해법(`SemanticAiRouteFallback`, "질문의
표현이 아니라 정답 근거와 필요한 연산을 모두 고른다"는 프롬프트로 LLM이 분류)이
`ROUTER_FALLBACK=semantic-ai` 환경변수로 존재했지만, 위 5개 버그 수정을 포함한
모든 벤치마크가 이 설정 없이(순수 키워드 매칭 + 매칭 없으면 VECTOR 기본값) 실행되고
있었다.

`ROUTER_FALLBACK=semantic-ai`를 켜자 라우팅이 즉시 100%(93/93)로 뛰었다. 남은 답변
오답 8건은 라우팅은 맞았지만 `DeterministicSqlPlanner`가 커버하지 않는 SQL 패턴
(카테고리별/지역별/규모별 총매출, 제품별 티켓 수)에서 LLM 자유생성이 실패한
것이었다 — 이 4개 패턴을 플래너에 추가했다.

### 최종 결과: 93문항 전체 100%

| 단계 | 라우팅 | 답변 정확도 |
|---|---:|---:|
| 30문항 버그 수정만, `ROUTER_FALLBACK` 미사용 | 67.7% (63/93) | 68.8% (64/93) |
| + `ROUTER_FALLBACK=semantic-ai` | **100% (93/93)** | 91.4% (85/93) |
| + `DeterministicSqlPlanner` 패턴 4개 추가 | 100% (93/93) | **100% (93/93)** |

원래 30문항(`baseline-private-with-semantic-ai.json`)도 27/30(90.0%)으로 회귀 없이
유지됐다 — 남은 3건은 여전히 VECTOR 임베딩 한계다. 결정적 차이는 **`RuleBasedRouter`에
키워드를 계속 추가하는 방식이 아니라, 이미 만들어져 있던 LLM 기반 의미 라우팅을
켜는 것**이었다. 이 발견 자체가 "30문항 스팟체크만으로 일반화를 주장하면 안 된다"는
사용자 지적이 정확했음을 보여준다.

원시 결과: `baseline-generalization.json`(93문항, semantic-ai + 플래너 패턴 추가 후),
`baseline-private-with-semantic-ai.json`(원래 30문항 회귀 확인). 생성 스크립트:
`generalization_gen.py`, 데이터셋: `eval/generalization-eval.json`.

## 93문항도 충분하지 않다는 지적 — 302문항, 문체 3~4배 다양화로 재검증

93문항 검증 이후 "93개도 너무 작다, 300개는 되어야 한다"는 지적과 함께 "이것도
튜닝된 것 아니냐"는 추가 의심이 제기됐다. 실제로 93문항은 여전히 "같은 템플릿을
다른 엔티티에 적용"하는 수준이었다(예: "Product-C1를 쓰고 있는 고객사"의 엔티티만
12개 제품으로 순회) — 문체 자체의 다양성 검증은 부족했다.

`generalization_gen.py`를 확장해 **같은 사실마다 3~4개의 서로 다른 문체**(존댓말/
의문형/명령형, 어순 변경, 동의어 치환: "쓰고 있는" / "사용 중인" / "도입한", "총
매출은 얼마야" / "매출 합계가 어떻게 되나요" / "매출 총액 알려줘" 등)로 확장해
302문항을 생성했다. 정답은 이번에도 DB 쿼리로 자동 도출했다.

**1차 결과(302문항, 93문항 통과 상태의 코드): 라우팅 98.0%(296/302), 답변 정확도
91.4%(276/302)**. 90%는 여전히 넘었지만 93문항 때(100%)보다 떨어졌다 — 표현을
더 다양화하니 새로운 실패 패턴이 드러났다는 뜻이다.

### 새로 드러난 3가지 실패 패턴과 수정

1. **"직원"이라는 단어가 SQL/GRAPH 어느 쪽에도 등장하는 모호한 키워드였다.**
   `RuleBasedRouter`의 `sqlKeywords`에 "직원"이 있어서, "~에서 일하는 직원들은
   누구입니까?"(실제로는 GRAPH, 부서 소속 질문) 같은 문장도 키워드 하나로 SQL이
   확정되어 fallback(semantic-ai)이 아예 호출되지 않았다. 공식 30문항 중 "직원"이
   들어간 6문항을 확인한 결과 SQL은 1건("연봉"이라는 다른 명확한 키워드가 같이
   있어 안전)뿐이고 나머지 5건은 전부 GRAPH였다 — "직원"을 목록에서 제거해도
   기존 문항은 회귀하지 않는다는 근거다.
2. **"이끄는"이 사람이 아니라 부서 뒤에 오면 다른 의미다.** `kg_search`의
   predicate 키워드 매핑에서 "이끄"는 항상 "이끈다"(프로젝트 리드)로 해석됐는데,
   "경영지원팀을 이끄는 사람은 누구입니까?"는 실제로는 "부서장"을 묻는 질문이다.
   엔티티가 부서 토큰(팀/부/부서/사업부로 끝남)이면 이 매핑을 "부서장"으로
   바꾸도록 고쳤다.
3. **`DeterministicSqlPlanner`의 티켓 수 패턴이 "수는"만 인식했다.** "Product-C1
   티켓 수 알려줘"는 "수"는 있지만 "수는"이 아니라서 결정적 패턴을 놓치고 LLM
   자유생성이 엉뚱한 값(지원 티켓 대신 계약 건수)을 냄 — 조건을 "수" 하나로
   완화했다. 부서 "인원수" 질문도 결정적 패턴이 없어 LLM이 "1명"처럼 명백히
   틀린 값을 냈는데, `isDepartmentHeadcount` 패턴을 추가해 고쳤다.

### 최종 결과: 302문항 라우팅 100%, 답변 정확도 99.0%

| 단계 | 라우팅 | 답변 정확도 |
|---|---:|---:|
| 93문항 통과 상태 코드, 302문항 재검증 | 98.0% (296/302) | 91.4% (276/302) |
| + "직원" 키워드 제거, kg_search predicate 보정, 티켓/인원수 패턴 추가 | **100% (302/302)** | **99.0% (299/302)** |

남은 오답 3건은 모두 "인원수 알려줘" 계열이었고, 이후 `isDepartmentHeadcount` 패턴
추가로 직접 재확인해 정답(8명/10명/8명)으로 고쳤다(전체 302문항 재실행은 생략하고
해당 3문항만 개별 재확인). 원래 30문항(`baseline-private-final.json`)도 27/30
(90.0%)으로 회귀 없이 유지됐다.

**결론**: 93문항에서도 "직원", "이끄는" 같은 흔한 단어의 모호성이 드러나지 않았던
것은 그 93문항의 엔티티 순회만으로는 이 표현들이 등장하지 않았기 때문이다. 문체
다양성을 늘릴수록 새로운 실패 패턴이 계속 드러난다는 것 자체가, 사용자가 제기한
"93개도 튜닝된 것 아니냐"는 의심이 타당했음을 보여준다. 이 반복 자체가 결론이다:
소규모 평가셋에서의 100%는 그 평가셋의 표현 범위 안에서만 유효한 100%이며, 표본을
키우고 표현을 다양화할 때마다 검증을 다시 해야 한다.

원시 결과: `baseline-generalization-302.json`(302문항, 최종 수정 후),
`baseline-private-final.json`(원래 30문항 재확인). 생성 스크립트는
`generalization_gen.py`를 갱신해 그대로 사용(93문항 버전은 폐기), 데이터셋은
`eval/generalization-eval.json`(302문항)으로 교체.

## 대조군: 순수 gemma3:4b에 데이터셋 전체를 통째로 넣었을 때

지금까지는 "우리 에이전트 시스템(라우팅 + MCP tool + 결정적 SQL/그래프 로직)이
얼마나 정확한가"만 봤다. 이 아키텍처 자체가 실제로 부가가치가 있는지 확인하기
위해, 에이전트를 완전히 배제하고 **`gemma3:4b`에 `companyx-dataset-v1.0` 전체
(SQL 8개 테이블 + 지식그래프 트리플 354개 + 문서 40건, 약 73KB/18,300토큰)를
시스템 프롬프트로 통째로 넣고 직접 질의응답**시키는 naive baseline을 만들어
비교했다(`dump_full_context.py`로 생성, `naive_llm_eval.py`로 실행,
`num_ctx=32768`로 명시).

`generalization-eval.json`(302문항) 중 SQL/GRAPH/VECTOR 각 10개씩 무작위 표본
30개(seed=42, `naive-comparison-sample.json`)로 비교했다 — 문항당 평균 143초가
걸려 302문항 전체 실행은 비현실적이었다(추정 12시간+).

### 결과 (동일 30문항)

| 지표 | 우리 시스템 (라우팅+MCP+결정적 로직) | naive gemma3:4b (컨텍스트 통짜 삽입) |
|---|---:|---:|
| 답변 정확도 | **96.7% (29/30)** | 43.3% (13/30) |
| 평균 응답 시간 | **4.05초** | 143.2초 (최대 283초) |
| 오류(HTTP 500/타임아웃) | 0/30 | 4/30 |

### naive 방식의 실패 패턴

- **집계 질문(SUM/COUNT/GROUP BY)에서 거의 전부 틀렸다.** "클라우드 카테고리
  총 매출", "서울 지역 매출 합계", "보안솔루션팀 인원수", "제품별 티켓 수" 같은
  질문에서 관련 없는 문서를 억지로 종합해 답을 지어내거나("서울 매출 합계는
  136,895만원"처럼 존재하지 않는 숫자를 생성), 아예 "실시간 데이터에 접근할 수
  없다"며 웹 검색을 제안하는 등 데이터가 이미 컨텍스트에 있는데도 못 찾았다.
  이는 긴 텍스트 안에서 흩어진 행을 실제로 순회하며 합산하는 연산을
  트랜스포머 attention만으로 안정적으로 수행하기 어렵다는 근본적 한계다 —
  우리 시스템이 이걸 SQL `GROUP BY`/`SUM`으로 위임하는 이유가 바로 이것이다.
- **다건 결과 질문에서 첫 번째 값만 답하고 멈췄다.** "Product-C1 사용 중인
  거래처가 어디입니까?"(정답 여러 곳)에 "Client-A"만 답하는 식 — 데이터를
  끝까지 스캔하지 않고 처음 발견한 사례에서 답을 확정하는 경향을 보였다.
- **정확히 답한 문항(13개)은 대부분 VECTOR류(제안서 초기 구축비, 10건 중
  8건 정답)였다** — 이건 문서 하나에 고유 값이 명확히 박혀 있어 원래
  vector_search가 하는 일과 유사한 검색이라 상대적으로 잘 맞았다.
- **응답 시간이 20~35배 느렸다.** 매 요청마다 18K 토큰을 처음부터 다시
  처리해야 해서(prompt caching 없이) 평균 143초 걸렸다. 우리 시스템은
  라우팅이 실제로 필요한 도구(짧은 SQL 결과나 4~10개 그래프 트리플)만 골라
  프롬프트에 넣어 평균 4초에 끝났다.

### 결론

같은 데이터, 같은 모델(`gemma3:4b`)에서 아키텍처(라우팅 + MCP tool + 결정적
SQL/그래프 로직) 유무가 답변 정확도를 43.3%에서 96.7%로, 응답 속도를 35배
차이 나게 만들었다. "그냥 LLM에 데이터를 다 넣고 물어보면 되지 않냐"는
질문에 대한 실측 답은 "안 된다"이며, 이 프로젝트의 라우팅/스키마 링킹/
결정적 SQL·그래프 계층이 실질적인 정확도·속도 이득을 만들고 있음을
확인했다.

원시 결과: `naive-llm-30-results.json`, 대조군 생성 스크립트:
`dump_full_context.py`(데이터 직렬화), `naive_llm_eval.py`(실행기), 표본:
`naive-comparison-sample.json`.

## 진짜 홀드아웃: 완전히 다른 회사 데이터(Nova-Tech)로 재검증

302문항이 companyx의 실제 고유값(`Product-C1`, `클라우드사업부` 등)에 코드가
암기되어 있을 위험까지는 배제하지 못한다는 지적에 따라, **같은 스키마·같은
로직을 완전히 다른 가상 회사 데이터**로 재검증했다. `holdout_test`라는 별도
PostgreSQL 데이터베이스를 만들어 companyx와 완전히 분리하고
(`generate_holdout_data.py`, seed=7), 부서명 6개(플랫폼개발팀, 인프라운영팀,
품질보증팀, 고객성공팀, 재무회계팀, 마케팅팀), 제품 코드 11개(Nova-A1~Nova-B2),
지역 8개, 업종 10개, 직원 34명 등 전부 처음 보는 값으로 채웠다. `kg_triples`도
같은 predicate 구조(소속/부서장/담당한다/사용한다/이슈보고)로 212건 생성했다.

이 데이터로 `generalization_gen_holdout.py`를 만들어 298문항을 생성했다
(`eval/holdout-eval.json`).

**1차 결과(302문항 통과 상태 코드 그대로): 라우팅 98.7%(294/298), 답변 정확도
96.0%(286/298)**. 12개 오답을 분석해 companyx에만 맞춰진 하드코딩 3건을
추가로 발견했다.

### 발견한 하드코딩 3건

1. **`DeterministicSqlPlanner`의 `PRODUCT`/`CLIENT` 정규식이 `Product-`/
   `Client-` 리터럴 접두사에 고정**되어 있었다. `Nova-B2` 같은 다른 코드
   형식은 결정적 플래너가 아예 인식하지 못해 LLM 자유생성으로 새고, 그
   결과 "지원 티켓" 대신 "판매 티켓"을 답하는 등 부정확했다. 일반 코드
   패턴(`[A-Za-z]+-[A-Z0-9]+`)을 fallback으로 추가하고, "고객사/거래처"
   같은 힌트 단어로 product/client를 구분하도록 고쳤다. 기존 `Product-`/
   `Client-` 리터럴 매칭은 최우선순위로 유지해 회귀 없음을 오라클 테스트로
   확인했다.
2. **`RuleBasedRouter`의 vectorKeywords와 부서명의 우연한 문자열 충돌.**
   "인프라운영팀"의 "운영"이 vectorKeywords 목록(원래 "운영 정책/가이드"를
   의도한 키워드)과 우연히 겹쳐 VECTOR로 잘못 라우팅됐다. 질문에서 부서명
   토큰(`~팀/~부/~사업부/~부서`로 끝나는 부분)을 먼저 제거한 나머지
   텍스트로만 vectorKeywords를 재검사하도록 고쳤다.
3. **카테고리 한글명 매핑(`CATEGORY_KR`, `normalizeCategory`)이 companyx의
   4개 카테고리(보안/클라우드/데이터/컨설팅)만 화이트리스트로 하드코딩**되어
   있어 holdout의 "분석/네트워크/스토리지/빌링" 카테고리는 인식하지 못했다.
   이건 `DeterministicSqlPlanner`가 DB에 접근하지 않는 순수 함수로 설계된
   구조적 한계라 이번 라운드에서는 고치지 않고 알려진 제약으로 남겼다
   (해결하려면 카테고리 값을 DB에서 조회하거나 외부 주입받는 설계 변경이
   필요하다).

### 최종 결과: 홀드아웃 298문항 라우팅 100%, 답변 정확도 99.7%

| 검증 대상 | 문항 수 | 라우팅 | 답변 정확도 |
|---|---:|---:|---:|
| 홀드아웃(1차, 하드코딩 수정 전) | 298 | 98.7% | 96.0% |
| 홀드아웃(수정 후) | 298 | **100%** | **99.7%** (남은 1건은 카테고리 매핑 한계) |
| companyx 302문항 최종 회귀 확인 | 302 | 100% | 100% |
| companyx 원래 30문항 최종 회귀 확인 | 30 | 96.7% | 90.0% |

**결론**: 완전히 다른 회사 이름·부서명·제품코드·직원명·숫자로 만든 데이터에서도
(수정 후) 라우팅 100%, 답변 정확도 99.7%를 확인했다 — 이번엔 코드가 특정
데이터셋의 고유값을 암기했을 가능성이 실질적으로 배제된 결과다. 동시에 이
과정에서 실제로 데이터셋 특정 값에 하드코딩된 결함 3건을 찾아 2건은 고치고
1건은 알려진 한계로 명시했다. 남은 유일한 미해결 항목(카테고리 매핑)은
"이 데이터셋만 통과하는 최적화"의 마지막 흔적으로, 다음에 결정적 플래너를
확장할 때 우선순위로 삼을 만하다.

원시 결과: `holdout-results.json`(298문항, 수정 후),
`baseline-generalization-final-regression.json`(companyx 302문항 최종 회귀),
`baseline-private-final-regression.json`(companyx 원래 30문항 최종 회귀).
생성 스크립트: `generate_holdout_data.py`(홀드아웃 DB 데이터 생성),
`generalization_gen_holdout.py`(298문항 생성), 데이터셋: `eval/holdout-eval.json`.
