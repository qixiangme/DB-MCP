# AIR 프레임워크 적용 리뷰

AIR의 가장 큰 장점은 적은 보일러플레이트와 빠른 기동이다. `defineTool`, `defineResource`,
플러그인 배열로 MCP 서버 계약을 짧게 표현할 수 있고, 이번 저장소에서도 agent 수정 없이 URL만
바꿔 Spring AI와 동일한 복합 평가 정확도를 냈다. 이는 AIR의 실질적인 장점이자 MCP 계약의
교체 가능성을 보여 준다.

다만 현재 `@airmcp-dev/core 0.3.0`을 운영 후보로 선택하려면 다음이 보강되어야 한다.

1. 인증·인가 예제가 필요하다. 현재 서버는 timeout 플러그인만 사용하며 SSE tool/resource와
   관리자 성격의 데이터 작업을 보호하는 표준 구성이 보이지 않는다.
2. timeout이 하위 DB/Ollama 작업의 취소까지 전파되는지 문서와 테스트가 필요하다. 응답 시간
   제한만으로는 이미 실행 중인 PostgreSQL 쿼리의 CPU·메모리를 회수하지 못한다.
3. `run_sql` 같은 고위험 도구에는 프레임워크 차원의 입력 길이, 동시성, rate limit, 출력 전
   streaming/byte budget 예제가 필요하다.
4. Node 이벤트 루프에서 CPU 작업을 수행하지 않는 가이드가 필요하다. 현재 구현의 토큰화와
   정렬은 작게 제한되어 병목 증거가 없지만, 로컬 reranking·대형 그래프 순회·토크나이징이
   추가되면 Worker Thread 또는 다중 프로세스가 필요하다.
5. 동일 계약 테스트에서 Tool뿐 아니라 Resource, 오류 스키마, 취소, 재연결과 세션 격리를
   검증할 공식 harness가 있으면 프레임워크 신뢰도가 높아진다.
6. 문서 적재처럼 서버가 소유하는 운영 작업과 read-only tool 계정을 분리하는 reference
   architecture가 필요하다.

이번 측정에서 AIR은 Spring AI와 정확도 93.3%로 같았고 p95는 약 9.8% 낮았지만, p50은 약
11.2% 높고 평균 컨텍스트도 9.8% 많았다. 검색과 SQL 가드 구현도 동일하지 않다. 따라서 AIR이
느리거나 DB 연결이 불안정하다고 결론 내릴 증거도, Spring AI를 버릴 결정적 이득도 없다.

현재 선택은 Spring AI다. 이유는 Java/Kotlin 스택 적합성만이 아니라 서버 소유 적재,
Spring 트랜잭션, 더 넓은 계약 테스트, 한 빌드 체계에서의 운영 일관성이다. AIR은 위 항목이
보강되면 동일 계약을 더 적은 코드로 제공하는 유력한 대안이다.
