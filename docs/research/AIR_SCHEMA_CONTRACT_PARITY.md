# AIR–Spring AI MCP 도구 계약 비교

## 목적

`agent-app`이 MCP URL만 바꿔 두 서버를 사용할 수 있다는 주장을 도구 이름뿐 아니라
응답 구조와 안전 경계까지 검증한다. 비교 대상은 같은 `main`의 Spring AI 서버와 AIR
서버이며, 런타임 프롬프트나 평가 문항은 변경하지 않는다.

## 발견한 차이

| 계약 | Spring AI | 변경 전 AIR | 변경 후 AIR |
|---|---|---|---|
| `get_schema.foreignKeys` | 제공 | 누락 | 제공 |
| `get_schema` 출력 예산 | 8,000자 | 4,000자 | 8,000자 |
| 예산 초과 응답 | 유효한 오류 JSON | 잘린 비정상 JSON 가능 | 유효한 오류 JSON |
| DB 오류 응답 | 유형화·내부 정보 마스킹 | 원본 오류 노출 | 유형화·내부 정보 마스킹 |

결정적 Node 테스트는 위 네 계약과 SQL 입력 오류를 포함해 5건을 검증한다.

## 동일 조건 탐색 실행

- 데이터셋: `eval/official-eval.json` 30문항
- 모델: Ollama `gemma3:4b`, temperature 0.0
- 라우터: `semantic-ai`
- 반복: 각 구현 1회
- 데이터: 같은 Docker PostgreSQL 볼륨
- 지표: 라우팅, 최종 답변, 지연, 요청 오류를 분리

| 구현 | 답변 | 라우팅 | 평균 지연 | 요청 오류 |
|---|---:|---:|---:|---:|
| Spring AI `main` | 63.3% (19/30) | 100.0% | 8,065ms | 0 |
| AIR `main` | 76.7% (23/30) | 100.0% | 8,150ms | 0 |
| AIR 계약 후보 | 76.7% (23/30) | 100.0% | 8,409ms | 0 |

이 수치는 1회 탐색 실행이므로 프레임워크 우열이나 정확도 개선 근거로 사용하지 않는다.
세 실행 모두 같은 복합 라우트에서 MCP 요청 제한 120초에 도달해 평균 지연이 크게
늘었다. Spring과 AIR 양쪽에서 재현됐으므로 특정 서버 구현에 원인을 귀속하지 않고
공통 MCP 클라이언트·동시 호출 경로의 차단 문제로 남긴다. 후보의
확실한 개선 근거는 답변 점수가 아니라 결정적 계약 테스트 0/4 충족에서 4/4 충족으로의
변화다. 반복 측정과 명시적 답변 채점 규칙이 완료되기 전까지 정확도 비교는 탐색 결과다.

## AIR 공급사에 전달할 피드백

1. 동시 도구 호출에서 응답 ID가 유실되거나 늦게 도착하는지 확인할 수 있도록 세션별
   요청 ID와 취소·타임아웃 진단 훅을 공식 API로 제공할 필요가 있다. 같은 현상이 Spring
   서버에서도 발생했으므로 AIR 고유 결함이 아닌 클라이언트 상호운용 문제일 가능성도 함께
   진단해야 한다.
2. 도구별 최대 출력과 오류 직렬화 정책을 플러그인으로 표준화하면 각 서버가 잘린 JSON과
   내부 오류 노출을 별도로 방어하지 않아도 된다.
3. 현재 설치 시 의존성 감사가 중간 3건, 높음 2건을 보고한다. 직접·전이 의존성별 영향과
   호환되는 업데이트 경로를 릴리스 노트에 제공할 필요가 있다.
4. `params` 문자열 선언과 handler 입력 사이에 정적 타입 계약이 없어 Spring의 어노테이션
   기반 도구 스키마보다 회귀 검출이 어렵다. TypeScript 타입 또는 스키마 추론 지원이 유용하다.

## 판정 기준

계약 테스트와 전체 서버 테스트는 통과했고 단일 반복 답변 정확도는 AIR 기준선과
동일했다. 그러나 120초 지연과 반복 수 부족이 남아 있으므로 즉시 채택안이 아니라
안전성·호환성 개선을 검토하는 Draft로 취급한다. 반복 측정에서 회귀가 나타나거나
공통 동시 호출 차단 문제를 분리하지 못하면 닫는다.
