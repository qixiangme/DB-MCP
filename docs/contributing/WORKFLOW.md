# 이슈와 PR 운영 절차

## 분류

| 유형 | 이슈 양식 | PR 양식 | 필수 증거 |
|---|---|---|---|
| 기능 | Feature | feature.md | 완료 조건, 테스트, 호환성 |
| 버그 | Bug | bug.md | 최소 재현, 원인, 회귀 테스트 |
| 벤치마크 | Benchmark | benchmark.md | 기준선·후보 원시 결과, 프로토콜 |
| 문서 | Docs | docs.md | 독자, 링크·명령 검증 |
| 리팩터링 | Refactor | refactor.md | 동작 보존, 성능 회귀 확인 |
| 보안 | Security | security.md | 위험 모델, 음성 테스트, 잔여 위험 |

PR 생성 화면에서 템플릿이 자동 선택되지 않으면 URL 끝에
`?template=benchmark.md`처럼 `template` 쿼리를 지정합니다.

## 흐름

1. 중복 이슈와 기존 벤치마크를 검색합니다.
2. 이슈에 문제, 범위, 완료 조건, 안전성 영향을 기록합니다.
3. `type/짧은-설명` 브랜치를 만들고 한 목적만 구현합니다.
4. 테스트와 벤치마크를 실행하고 실패도 보존합니다.
5. 목적에 맞는 PR 양식으로 이슈를 연결합니다.
6. 리뷰에서 정확성, 안전성, 재현성, 문서 일치를 확인합니다.

모든 이슈와 PR에는 다섯 평가항목 중 주 평가항목 하나를 지정하고, 필요하면 보조 평가항목도
기록합니다. 또한 기준 브랜치, 현재 문제의 증거, 예상 상승 폭, 평가 문구와의 연결,
구현 전후 검증 방법, 안전성, 위험과 되돌리기를 남깁니다. 점수 상승 폭은 심사 결과가 아니라
검증할 가설로 표현합니다.

권장 브랜치 접두사는 `feature/`, `fix/`, `benchmark/`, `docs/`, `refactor/`,
`security/`, `chore/`입니다. 강제 푸시가 필요하면 리뷰가 시작되기 전에 알리고,
공유 브랜치의 이력은 덮어쓰지 않습니다.

## 리뷰 게이트

- 정확성: 변경 전 실패/변경 후 통과 또는 명시적 기대값이 있는가?
- 안전성: 입력 검증, 읽기 전용 SQL, 최소 권한, 비밀정보 제거를 확인했는가?
- 체계성: 이슈·PR·커밋·결과 파일이 추적 가능한가?
- 재현성: 버전, 모델, 설정, 명령, 원시 결과가 남아 있는가?
- 회귀: 공식 평가셋과 단위 테스트의 허용 한도를 통과했는가?

## 매일 개선 검토

예약 작업은 매일 열린 이슈·PR, 최근 커밋, 검사 결과, 벤치마크와 문서를 확인하고 다음
다섯 항목을 모두 검토합니다.

1. 프로젝트 구조 및 코드 완성도
2. 오픈소스 프로젝트의 발전 가능성
3. 개발 문서의 구체성
4. 프로젝트 혁신성
5. 프로젝트 팀워크

한 번의 검토에서 굵직한 후보를 여러 개 탐색하되, 다음 조건을 모두 만족한 후보만 게시합니다.

- 기존 이슈·PR과 중복되지 않는다.
- 최소 0.1점 이상 기여할 수 있다는 구체적인 가설과 현재 증거가 있다.
- 독립 브랜치에서 구현하고 테스트 또는 벤치마크로 전후를 비교할 수 있다.
- 평가 문항·정답·키워드를 구현이나 프롬프트에 복사하지 않는다.
- 비밀정보와 내부 자료를 원격에 올리지 않는다.

조건을 만족하는 후보가 없으면 이슈나 PR을 만들지 않습니다. 후보별로 한국어 이슈와
독립된 드래프트 PR을 만들며 자동 병합하지 않습니다. 측정 결과 개선이 없거나 회귀하면
원시 결과와 판정 근거를 남기고 PR과 이슈를 `계획하지 않음`으로 닫습니다. 완료 조건이
모두 충족된 이슈는 확인 댓글을 남긴 뒤 `완료됨`으로 닫습니다.
